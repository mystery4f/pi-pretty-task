# 0016 — 子任务的 id 不携带父与序号

## 状态
已接受（2026-11-14）

## 背景

cmd loop 每次触发会创建一条普通的 process 任务（ADR 0014），链的每一格也是。它们与普通任务的区别只有 `parentId` 与序号，于是自然出现一个问题：id 要不要把「属于谁、第几次」编进去，例如 `bg-9xk2q-47`。

## 决策

**不编。子任务用同一套 `bg-` + 5 位随机 id，父与序号作为字段存在，不在 id 里。**

- `createId(kind)` 只由 kind 决定前缀：`bg-` / `lp-` / `lc-` / `ch-`。没有任何「继承父前缀」的分支。
- 触发记录必须带 `parentId`（所属循环）与 `fire`（第几次触发）；链步骤带 `parentId`（所属链）与队列位置（由链的 `cursor` 与 `steps` 决定，不落在步骤上）。
- 碰撞检查仍在会话级命名空间内：从磁盘恢复的 id 视为已占用。
- **人读的别名放在文本里，不放进 id**：工具输出与面板写成 `api-watch#47 (bg-7k2m9)`。id 短、可重抄、不随序号变长。

## 理由

- id 是引用键：它出现在消息、日志、通知与存储中，会被抄进下一轮对话。编码序号会让它变长（8 位宽度保不住），形状随来源变化，读的人还要知道编码规则才能查。
- 序号与父都是可变数据；id 一旦写入就不该变化。触发可以跳过、可以被历史上限裁掉，编码进去只会产生空洞型 id。
- 生成路径只有一条：任何 process 任务都走同一个 `createId`，不必为「父循环的子任务」写第二套。

## 后果

- 看到 `bg-7k2m9` 不能立刻知道它属于哪个循环，必须看 `parentId` 或面板的父行 —— 代价由别名写法补偿。
- 触发的展示需要拼接 `name#seq` 与 id 两段，属于渲染层的事，不进存储。
