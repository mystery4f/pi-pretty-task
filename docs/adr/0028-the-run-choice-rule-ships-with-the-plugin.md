# 0028 — 起命令前的三选一随插件一起装好

## 状态

已接受（2026-11-28）

## 背景

后台模式的全部收益，是「起完就走」。实测里它没发生：最近 10 天 68 个会话、480 次 `pretty_task_bg_run`，只有 19 次带 `wait: true`（4.0%）；而 `pretty_task_bg_wait` 被调 256 次，其中 161 次的上一个工具调用就是本会话刚起的 `bg_run`——33.5% 的 run 后面都跟着一个本可以在那次 run 里等掉的 `bg_wait`。ADR-0025 / ADR-0027 造出来的阻塞通道基本没人走，多出来的却是一个来回。

成因不在机制，在选择：`wait` 参数描述只讲参数干什么，`runDescription` 只讲什么时候该用后台，没有任何一处讲**什么时候该等**。模型因此默认「起后台、再等」，把一次调用能换来的结果拆成两次。

写进配置文件也行不通：这份规则得跟着插件走，用户装完就该生效，不该由人抄进某台机器的 AGENTS.md。

## 决策

### 四格

每次起命令之前先归一次类，只有四种结局，各自对应一个工具形态：

- **会自己结束 + 结果就是下一步的前提 + 预计 ≤600 秒 + 此刻没有别的活可干**：四条全中才 `pretty_task_bg_run` 带 `wait: true`，并且必须带 `waitSeconds`（预计秒数 + 60，上限 600）。没有 `waitSeconds` 的阻塞等待没有边界，调用方的耐心只剩 Esc——而 `waitSeconds` 到点只结束等待、不动任务，是最便宜的一条退路（ADR-0027）。
- **会自己结束，但结果现在不用，或预计超过 600 秒，或估不出时长，或手上有别的活可以先干**：真后台，不带 `wait`。最后一支是这条规则的重点：等的收益是省一个来回，代价是把这一轮钉死在这个命令上；只要还有别的活能在它跑着的时候干，钉死就是净亏。先干那件活，结果回头用 `pretty_task_bg_logs` / `pretty_task_bg_grep` / 对更早起任务的 `pretty_task_bg_wait` 取——这一格是 `bg_wait` 唯一合法的用法，等的是更早起的任务，不是刚起的。
- **几秒内结束**：普通 `bash`。给一次 `ls` 造一条 Task 记录是纯开销，返回的 task id 还得再查一次。
- **永不结束**（dev server、watcher、`tail -f`）：起一次后台，之后用 `pretty_task_bg_logs follow` 看增量。绝不把 `tail -f` 当任务起——任务自己不会结束，等它等于把一次调用挂在永不到来的事件上。

外加一条否定：**不对上一次调用刚起的任务再 `bg_wait`**。要结果就在那次 run 里等；那一格要么是「必须等」，要么根本不该现在要结果。

### 落点：`promptGuidelines`，不是配置文件

规则以编译期常量写进两个工具的 `ToolDefinition.promptGuidelines`（`pretty_task_bg_run` 三段、`pretty_task_bg_wait` 一段），pi 把它们拼进系统提示词的 Guidelines 段（`buildRules(selectedTools, toolGuidelines, promptGuidelines)`）。装好插件，规则就在每一次请求里，不需要任何配置。

选这条接缝是因为它是 pi 的既有接口，也因为缓存：

- 常量的成本只付第一轮。本项目改动前三个会话的实测命中率是 93.9% / 95.6% / 98.2%，第一轮永远是 miss（61–66k input），之后 48 / 237 / 1603 轮里只有 1 / 9 / 17 轮 miss。
- 随轮次变化的文字（当前时间、任务计数、任务列表）会让**每一轮**都 miss，所以 guideline 文本里禁止出现这些。单测把这一点钉住：文本里不许有 ISO 日期、`bg-` 开头的 id、`N tasks/runs/running` 这类计数。
- `before_agent_start` 里改 `promptGuidelines` / `sections`，pi 只把变化的部分补成一条 system 消息，已缓存前缀仍然有效；更激进的做法（返回 `systemPrompt` / `forceSystemPrompt`）是整段替换，必然 miss，不用。

工具描述同样只吃常量：`runDescription` 里那句「什么时候带 `wait`」写死，模板名部分照旧受 `TEMPLATE_BUDGET = 300` 约束，整条描述连同最坏情况的模板列表钉在 900 字符以内（单测）。

### 运行时提示

`bg_wait` 命中「本会话上一条 `bg_run` 刚起、且那次没带 `wait`」这条任务时，在结果末尾追加一行「下次把等待放进那次 run」。只在检测到该模式时出现，事后不再重复——它是一次纠偏，不是每轮都会重付的提示词。

## 判据

证据来自会话记录和仓库里的脚本，不来自印象。`scripts/wait-stats.mjs` 复现两个数：

- `wait: true` 占 run 的比例；
- run → wait 相邻率：同一会话工具调用序列里，`bg_wait` 的上一个调用是 `bg_run` 的次数，占 run 的比例。紧邻定义就是这个，别的都不算。

同一脚本顺带按轮打印 `cacheRead / (input + cacheRead)`，用来确认注入没有把缓存打穿：规则的文字是常量，所以只有每个会话的第一轮应当 miss。

基线（10 天窗口，脚本默认参数，改动前的会话）与改动后的探针批次（六条固定 prompt，`group/deepseek-flash`，`--since 2026-11-28T07:41:30Z`）：

| 指标 | 改动前 | 改动后（六条探针） |
|---|---|---|
| 会话数 | 68 | 6 |
| `bg_run` | 480 | 3 |
| `wait: true` | 19（4.0%） | 0（0.0%） |
| `waitSeconds` | 2 | 0 |
| `bg_wait` | 256 | 0 |
| run → wait 相邻 | 161（33.5% of runs，62.9% of waits） | 0（0.0%） |
| 逐轮缓存命中 | 会话内第二轮起 99% 上下 | 第二轮起 99.0–99.7%，只有每会话第一轮 miss |

探针批次的 `wait: true` 为 0 是这批 prompt 的正确结果，不是规则失灵：六条 prompt 里没有一条落在「结果正是下一步的前提 + 手头没别的活」这一格上——会自己结束又在几秒内的那条归 `bash`（第 1、4、5 条），要并行或估不出时长的归真后台（第 2、3、6 条）。判据要看的是相邻率与缓存两行：相邻率从 33.5% 掉到 0，缓存没有出现挨轮 miss。

复现方式：`node scripts/wait-stats.mjs`（默认 10 天），或 `--since <ISO>` / `--session <子串>` 只统计某一批会话。

## 不变的东西

- ADR-0025 / ADR-0027 的机制不动：四种等待结束方式、`waitSeconds` 只结束等待、`ctrl+shift+b` 放走调用，全部照旧。
- 默认值不动：不写 `waitSeconds` 的 `wait: true` 仍然无上限。这条 ADR 只规定「何时该选它」，不改变「选了之后默认等多久」。
- 规则不写进任何 AGENTS.md：它属于插件，不属于某一台机器的配置。
