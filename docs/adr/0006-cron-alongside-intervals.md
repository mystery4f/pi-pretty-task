# Loop 的调度吃两种语法：间隔简写与五段 cron

一条 loop task 的调度可以写成间隔简写（`30s`、`10m`、`2h`）或五段 cron 表达式（`分 时 日 月 周`，支持 `*`、列表、区间、步长）。两者都解析成同一个 `nextFire(after: number): number | null`，调度器只认这个函数，不关心原文长什么样。

## Considered Options

- **只做间隔**：实现最省，但“每个工作日 9:00”这类最典型的用法表达不出来，而这正是用户要 cron 的理由。
- **只做 cron**：一个语法就够，但分钟是最小粒度，调试期想看一次唤醒得等一分钟；而且想让 agent 每 10 秒自检一次就写不出来。
- **两种都收（采用）**：间隔负责秒级与固定步长，cron 负责挂钟时间；代价是多一条解析路径与两套错误文案。

## Consequences

- 解析与预设计算独立成模块，输入原文 + 当前时刻，输出下次触发时刻或“永不”；调度器、面板、测试都只依赖这个出口。
- 六段（带秒）的表达式明确拒绝，并提示改用间隔简写 —— 避免“写完才发现粒度不对”的隐性行为。
- 非法表达式在 `loop_create` 当场报错，附一个正确示例；不允许存进去之后静默不触发。
- 面板同时显示原始表达式与算出来的下次触发时刻，让“为什么还没触发”可以直接看出来。
- 秒级粒度仍然只由间隔提供，因此 pump 的频率必须支持秒级，cron 只是恰好很少用满这个频率。
