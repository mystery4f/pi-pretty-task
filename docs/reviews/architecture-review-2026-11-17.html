问题　 input.ts、list.ts、detail.ts 三个文件合计 1,470 行，每个导出函数的第一个参数都是 panel: TasksPanel，一共碰到 40 个不同成员、270 次（184／44／42）。 它们不是模块，是把一个类的 this 拆成了三份文件；唯一能调的接口在组件边缘——render(width)、handleInput(data)、settle()。 所以 2,580 行测试全部只能靠"按键字符串进、整屏文本出"来验证：改一个页面的内部状态，要穿过键盘和边框才能看到结果。

  • · 84 行注释没有宿主：tasks-panel.ts:406-489 只有 JSDoc 与空行，没有任何声明，类在 490 行直接闭合——文件是按行数切的，不是按概念切的。
  • · 25 个导出只有一个调用者：input.ts 导出 25 个函数，全仓库只 import 了 handlePanelInput 一个（tasks-panel.ts:22）；其余的 export 只让"模块"看起来像个模块。
  • · 互相引用：list.ts:38 从 tasks-panel.js 取 type TasksPanel，tasks-panel.ts:23 又从 ./list.js 取 renderList／stepRecord；detail.ts:36 还得借 list.ts 的 chainPlace／foreign／stepRecord 才知道一行怎么排。
  • · 测试从不碰字段：2,580 行用例里对 panel.rows／panel.mode／panel.query 的直接赋值是 0 次，只走 handleInput／settle／render——真正的接口是 3 个方法，类却同时公开 23 个字段与 12 个方法。
  • · 意外 barrel：tasks-panel.ts:35-36 的 export * from "./format.js" 与 "./model.js" 让组件成了转口，测试因此绕道它去取 PANEL_FILTERS。

方案　 把面板状态收成一个模块，接口按意图命名而不是按字段：select(id)、cycleFilter()、startSearch()、openDetail(id)、 scrollBy(n)、snapshot(): PanelSnapshot。三个渲染器改成只吃只读快照的纯函数，input.ts 退化成一张键位表（key → intent）。 字段从公开变成私有，rows 这类中间量由 applyFilters() 自己维护。

  • · 渲染可以脱离键盘测试
  • · 状态迁移可以脱离渲染测试
  • · 换一个键位只动键位表
  • · 40 个可写成员变成 1 个快照出口
  • · 三个页面共享同一个状态类型
  • · tick 刷新不必再猜哪些字段是"派生"
与既有决策的关系　不推翻 ADR-0012（三页共享一套键盘模型）——键位表仍然是一个模块， 被改的是状态怎么被写，不是有哪些键。ADR-0003 的"面板不留痕、只留状态栏"也不受影响。 代价：面板内部会多一个类型（PanelSnapshot），渲染器签名要从 (panel, width) 改成 (snapshot, width, theme)。

问题　 ADR-0009 那条规则——"唤醒要等 agent 空闲，并且绑定它自己那一轮"——现在只以闭包形式存在： 一个布尔 agentIdle、一个谓词 isDeliverable（src/index.ts:371）、一个函数 flushWakes（src/index.ts:382）， 被 4 处调用（session_start、turn_end、agent_settled、返回的 controller）。 "什么时候可以把一条 prompt 送进会话"没有任何接口能回答，而 LoopWakes 只有 66 行，是个数组加 drain—— 真正的策略不在它里面。后果很直接：test/unit 里没有一个文件 import src/index.ts， 要验这条规则必须拉起整个扩展（假 ExtensionAPI、临时目录、真子进程）。

  • · 四条唤醒路径收成一次 pump
  • · 策略可以用假时钟单测
  • · 组合根回到装配职责
  • · "空闲"不再是一个裸布尔
  • · 关停时的丢弃行为有单一入口

问题　 options.sessions ?? new TaskSessions({ now }) 出现在两处（process-tasks.ts:323、chain-tasks.ts:104）。 组合根（index.ts:163）今天确实传了同一个实例，所以线上看不出问题——但只要某个调用方（包括测试）忘了传， 同一目录立刻有第二个缓存和第二支笔，而且失败方式是"写进去了但看不见"，不是报错。 第三条规则在 LoopTasks.readSession（810-813）：owned 就用 session()，否则 read()—— 而 read() 返回的是重新解析的一份（新的 TaskStore），谁顺手改它，谁就写出第二代记录。

方案　 sessions 变必填（默认值删掉）；把 read() 的语义显式化——"只读翻开，不收养、不可写"， 并让 LoopTasks 那条三元判断收进 TaskSessions 自己，调用方只问一次。 一个目录一个缓存、一支笔，是 ADR-0010（recency 落盘）与 ADR-0011（id 前缀）共同依赖的前提。

  • · 第二个写者不可能出现
  • · "读到的是不是可写的"有明确答案
  • · 测试不再意外走默认分支
  • · 三条所有权规则收成一条
为什么是 Strong　其它候选是结构问题，这条是正确性问题：它不会让你多写代码，只会在某天让一条记录静默消失。 改动很小，可以先做。

问题　 六个工具各自先查 tasks、再查 chains，失败文案 No background task with id … in this session. 在同一个文件里出现 7 次， 连变量名都有三种写法（wantedId／params.id／id）。 后果是工具层即使与队列毫无关系，也必须拿到 chainTasks——六个工具里真正需要链的只有 run 的 after 参数。
